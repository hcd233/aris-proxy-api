# 服务并发容量上限压测（2026-10-17）

> 目标：放开 CPU limit 到机器全部核数后，测出服务**最多能稳定维持多少条 SSE 长连接流**。
> 前置基线：`2026-10-16-baseline-three-apis.md`
> 原始数据：`raw/2026-10-17-capacity/`

## 1. 结论

**安全容量约 200 条并发流。**

| 并发档 | 完成请求(120s) | req/s | CPU 峰值 | 内存峰值 | 连接错误 | 判定 |
|--------|---------------|-------|---------|---------|---------|------|
| 50 | 193 | 1.61 | 407m | 175Mi | 0 | ✅ 安全 |
| 100 | 281 | 2.34 | 554m | 186Mi | 2 | ✅ 安全 |
| **200** | **296** | **2.47** | 786m | 297Mi | 5 | ✅ **吞吐峰值** |
| 400 | 251 ↓ | 2.09 ↓ | 824m | 453Mi | 120 / 0（两次差异大） | ⚠️ 不稳定 |
| 800 | 210 ↓ | 1.75 ↓ | — | — | 371 | ❌ 退化 |
| **800（复测）** | **0** | **0** | — | — | **13605** | ❌ **机器重启** |

**拐点在 200~400 之间**：200 并发时完成请求数与吞吐（2.47 req/s）同时达到峰值；
超过后两者齐降，连接错误随并发陡增。

**关键洞察：瓶颈不在服务本身。** 即使在 400 并发（出现大量连接错误时），
pod 的 CPU 仅用 824m（limit 2000m 的 41%）、内存仅 453Mi（512Mi limit 的 88%），
**两者都未饱和**。真正的约束来自机器本身：

- 机器只有 **2 核 CPU / 3.9GB 内存**，且上面同时跑着 PostgreSQL、Redis、openresty、
  pgadmin、portainer 等 8+ 个容器
- `tcp_max_syn_backlog = 256`（偏低），高并发建连时 SYN 队列易溢出
- 无 swap，内存一旦耗尽直接 OOM

## 3. 方法

### 3.1 绕过限流（必需）

上一轮基线暴露了硬天花板：LLM 转发路由限流 **100 次/分钟 per API Key**。
按 mock 流平均 19 秒算，**并发超 ~30 即触发限流**，测不到真实容量。

对策：**多 Key 分摊**（限流按 API Key 维度）——
建 20 个压测 Key（`proxy_api_keys` id 9~28，命名 `lt2-2026-10-17-*`），
合计 2000 req/min ≈ 33 req/s，足以支撑 600+ 并发长流。

wrk 脚本改造为支持 Key 池轮换：

```lua
local keys = {}                      -- LT_KEYS 逗号分隔优先，回退单 Key API_KEY
local idx = 0
function request()
  idx = idx + 1
  return wrk.format("POST", nil, {
    ["Authorization"] = keys[(idx % #keys) + 1], ...
  }, body)
end
```

（wrk 每线程独立 Lua 状态，故各线程独立轮换；单 Key 模式仍兼容。）

### 3.2 阶梯加压

档位 50 / 100 / 200 / 400 / 800，每档 `-t4 -c<N> -d120s --timeout 300s`，
档间冷却 20s；每档在压测中段（45s）与结束各采一次 `kubectl top pods` 记录
CPU/内存，用于区分「服务饱和」与「宿主饱和」。

## 4. 结果与分析

### 4.1 吞吐与延迟

| 并发 | 完成请求 | req/s | 平均延迟 | p50 |
|------|---------|-------|---------|-----|
| 50 | 193 | 1.61 | — | — |
| 100 | 281 | 2.34 | — | — |
| 200 | 296 | **2.47** | — | — |
| 400 | 251 | 2.09 | — | — |
| 800 | 210 | 1.75 | — | — |

完成请求数在 200 档见顶后回落——**不是服务处理不过来，而是连接建不起来**。

### 4.2 连接错误的性质（重要）

观察到 connect 错误随并发陡增（200→5、400→120、800→371），但做了两组对照后确认
**这不是服务的连接建立能力问题**：

1. **快速端点对照**：`/health` 在同样 400 并发下跑出 **39186 请求 / 1302 req/s / 0 错误**。
   说明服务端与中间层的连接建立完全没问题。
2. **重复性**：400 并发的两次运行 connect 错误分别是 120 和 0——不稳定，指向
   **瞬时 SYN 洪峰**而非稳态限制。

结合 `tcp_max_syn_backlog=256`：wrk 启动瞬间数百个 SYN 同时到达，
超出 backlog 的部分被丢弃（`tcp_abort_on_overflow=0` 故静默丢弃），
客户端 TCP 层重试，重试不及的记为 connect 错误。**长流场景放大**了这一效应：
长流下连接周转慢，堆积窗口更长。

### 4.3 机器重启事故（800 并发复测）

第二次 800 并发运行出现 **0 完成请求 + 13605 connect 错误**。

排查结果：

- 宿主 `uptime` 变为 **3 分钟**（上次 reboot 在 10 天前）→ **机器在 16:54Z 重启**
- 当时 load average 达 **3.92**（2 核机器 = 严重过载）
- 两个 pod 各重启 2 次，`exitCode=1`（非 OOMKilled）
- pod 崩溃日志根因：

```
[Server] Start server panic  {"error": "dial tcp: lookup redis: i/o timeout"}
  at internal/infrastructure/cache.InitCache() redis.go:43  (lo.Must)
```

**因果链**：800 并发长连接 → 宿主过载 → 机器重启 →
pod 重启时 **CoreDNS/Redis 在该负载下不可达** → `InitCache()` 的 `lo.Must` panic →
容器退出 → 反复重启（BackOff）。

即：**服务本身没有被压垮，是被宿主资源耗尽带崩的**；而重启期的启动强依赖
（Redis 必须可达，否则 panic）放大了故障——**这是一个真实的可用性隐患**。

## 5. 结论与建议

1. **容量边界**：本机（2 核/3.9GB，含 8+ 共存容器）上，
   建议把并发流控制在 **200 条以内**；400 已出现不稳定，800 会拖垮宿主。
2. **瓶颈定位**：服务的 CPU/内存余量充足（41% / 88%），
   **限制来自宿主规格与网络栈配置**，不是代码或 pod limit。
3. **若要提升容量**，按收益排序：
   - **换更大规格的机器**（核数 + 内存）——最直接，当前 2 核是硬约束
   - **调大 `net.core.somaxconn` 与 `net.ipv4.tcp_max_syn_backlog`**（256 → 4096），
     缓解建连洪峰
   - 将 PostgreSQL / Redis 等从本机分离，避免与转发服务争抢资源
4. **可用性改进（建议跟进）**：`InitCache()` 用 `lo.Must` 在 Redis 不可达时直接
   panic，导致依赖抖动即崩溃循环。改为**带重试的启动**（指数退避重试若干次再失败）
   能显著提升重启韧性。
5. **压测注意**：本机压测时留意宿主 `load average` 与 pod restart 计数；
   出现 connect 错误激增即应停止加压。
