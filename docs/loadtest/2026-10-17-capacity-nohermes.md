# 容量复测：停掉 hermes 后（2026-10-17）

> 上一轮：`2026-10-17-capacity-limit.md`（结论：安全容量约 200，800 并发导致机器重启）
> 本轮变量：**停掉 `1Panel-hermes-agent`**（释放 704MB 内存），复测结论是否有变化。
> 原始数据：`raw/2026-10-17-capacity-nohermes/`

## 1. 结论

1. **内存改善提升了韧性，但没提升容量**：800 并发**不再导致机器重启**（上轮重启），
   但有效吞吐未实质提升——因为**真正的瓶颈是 CPU，不是内存**。
2. **安全容量仍为 100~200 条并发流**；200 并发时 p50 已从 23.9s 恶化到 42.6s（排队）。
3. **CPU 是硬瓶颈且被多方瓜分**：压测中宿主 `id=0%`（完全饱和），
   其中 **软中断占 30%**，容器侧 openresty 38.8%、postgresql 35.9%、xray 26%。

## 2. 变量：停掉 hermes

| 项 | 停之前 | 停之后 |
|----|--------|--------|
| `1Panel-hermes-agent` | 运行，753MiB | **已停**（`restart=no`，重启策略原为 `always`） |
| 内存 available | 1495 MB | **2221 MB**（+726MB） |

## 3. 结果对比

| 并发 | hermes 开：完成 / req/s / 错误 | hermes 关：完成 / req/s / 错误 | hermes 关 p50 |
|------|------------------------------|------------------------------|--------------|
| 100 | 281 / 2.34 / 2 | 290 / 2.41 / 0 | 23.87s |
| 200 | 296 / 2.47 / 5 | 212 / 1.77 / 2 | **42.56s** |
| 400 | 251 / 2.09 / 120 | 258 / 2.15 / 60 | 40.51s |
| 800 | 210 → **0**（机器重启）/ 1.75 / 371→13605 | **658** / 5.48 / 902 | **4.44s** ⚠️ |

**如何正确读这张表**：

- **800 档的 658 不是真实容量**。其 p50 仅 **4.44s**，而 mock 流的期望时长是 19 秒——
  说明这批"完成请求"绝大多数是**快速失败**（连接建立后被立即关闭），叠加 902 个 connect 错误。
  真实可用的流仍是 100~200 档（p50 20~42s，符合流时长分布）。
- **200 档 p50 从 23.87s 涨到 42.56s**，是典型的**排队效应**：并发已打满处理能力，
  新请求要等前面的流腾出资源。
- 800 档不再崩溃这一点的价值在于**韧性**：内存余量让系统在极端压力下不再 OOM/重启，
  但吞吐上限没变。

## 4. CPU 分布（关键诊断）

400 并发压测进行中采样：

```
%Cpu(s): 37.0 us, 33.3 sy, 0.0 ni, 0.0 id, 0.0 wa, 0.0 hi, 29.6 si
```

- **`id = 0%`**：CPU 完全饱和
- **`si = 29.6%`**：**软中断**——大量网络小包（SSE 分片 + TCP 头）的中断处理开销
- `us 37%` + `sy 33%`：用户态与内核态各占三分之一

同时刻容器 CPU：

| 容器 | CPU% | 说明 |
|------|------|------|
| `1Panel-openresty` | **38.76%** | 反代转发 SSE 长连接（双向流式转发开销） |
| `postgresql` | **35.93%** | 审计 + 会话/消息落库（每请求都写） |
| `xray` | **26.05%** | 本机代理服务（`teddysun/xray`），与服务无关但争抢 CPU |
| `aris-proxy-api` pod ×2 | ~40%（合计） | 转发链路本身 |
| `redis` / 其他 | <1% | — |

**2 核被瓜分**：openresty 0.78 核 + postgresql 0.72 核 + xray 0.52 核 + 软中断 0.6 核
≈ 已超过 2 核，服务 pod 只能抢到约 0.4~0.8 核。

**这解释了「pod CPU 只用 41% 却达不到更高并发」**：不是 pod 不想用，
而是宿主根本没有剩余算力给它。

## 5. 提升容量的可行路径（按收益排序）

1. **换更多核的机器**——当前 2 核是硬约束，且被 4 类负载瓜分。
2. **把 PostgreSQL / Redis 迁出本机**——DB 在压测中吃掉 36% CPU（审计/落库是写放大源头）。
3. **移除或迁走 xray**——它占 26% 且与服务无关。
4. **降低网络开销**：
   - 调大 `net.core.somaxconn`（现 4096 尚可）与 `net.ipv4.tcp_max_syn_backlog`（现 **256**，偏小）
   - 减少软中断开销（如启用 GRO/TSO、调整中断亲和性）
5. **考虑反代效率**——openresty 38.8% 说明 SSE 双向转发有成本，可评估更轻的方案。

## 6. 未覆盖 / 待办

- `xray` 在压测中占 26% 的原因未深究（是否与压测流量路径相关未确认）
- 未做「迁出 DB 后」的对照测量
